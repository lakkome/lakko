|---|---|

### C-57 — Witness co-signing for KT-log split-view resistance (G-30 #1, ADR-0020 + ADR-0039 K-of-N quorum)

| ID   | Title |
|---|---|
| C-57 | An operator root is trusted by a client only when it carries BOTH the operator signature AND a valid co-signature from a build-time-pinned, independent witness. The witness (`services/witness`) co-signs a root ONLY after verifying a Merkle consistency proof (RFC 6962 §2.1.2, `crates/lakko-transparency/src/merkle.rs` `verify_consistency` — reconstructs both roots) that it append-only-extends the witness's last-co-signed root; two divergent forks cannot both extend one root, so the operator cannot fork alone (the honest witness refuses → 409). The cosig is a 105-byte blob (`version ‖ tree_root(32) ‖ log_size(8 BE) ‖ sig(64)`, domain `lakko/transparency/witness/v1`, distinct from the operator root sig); the FFI is verify-only (`verify_witness_cosig` — signing stays server-side). All three clients run `witnessGateRefuses` immediately after the no-rollback gate in `verifyIdentityInLog` + `verifyRotationChain`: missing/invalid cosig → `mismatch` (fail-closed, invariant #4); no pinned witness key → operator-only transition posture. `services/transparency` co-signs-on-read (fresh head-root sig, cached cosig keyed on `(tree_root, log_size)`, re-obtained only on growth; witness unreachable → serve None, never stale). Strengthens invariant #4 (root gate needs operator AND witness) + #6 (rotation anchored to a non-forkable root). The cosig + consistency proof are public artefacts over public roots (invariant #2); the witness persists only roots/sizes, never accounts (invariant #5). Closes G-30 finding 1 for the single-witness model. **K-of-N quorum now IMPLEMENTED ([ADR-0039](../adr/0039-kt-log-witness-quorum.md))** — the root gate now needs the operator signature AND ≥ K valid co-signatures from DISTINCT keys in a build-time-pinned witness key set of size N (`verify_witness_quorum`, dedup-by-distinct-key so a replayed / duplicated cosig can never inflate the quorum; the transparency service fans out to N witnesses best-effort and serves `witness_cosigs_b64: Vec<String>`, the clients enforce the threshold fail-closed); so the operator must corrupt K independent witnesses, not one. N=1/K=1 is byte-for-byte the single-witness gate. Residual: operator + K COLLUDING witnesses — closed in practice ONLY under INDEPENDENT witness operation (distinct trust domains; a deploy/ops property, not code — a single operator running all N witnesses gains nothing) + independence-as-deploy-property. Fuzz: `verify_consistency` + `verify_witness_cosig` + `verify_witness_quorum`. `lakko-security` APPROVE-WITH-NOTES |

### C-58 — Auth-signed backup-head rollback commitment (G-11, ADR-0037)

| ID   | Title |
|---|---|
| C-58 | A storage-tier backup **rollback** (serving a restoring client an older, cleanly-opening envelope) is detected by an auth-signed **backup head** committed atomically inside the one opaque storage blob. `BackupHead` (`crates/lakko-attest/src/backup_head.rs`) is a 129-byte fixed-layout Ed25519 blob binding `(account_id, backup_version, envelope_hash, signed_at)`, domain `lakko/backup-head/v1` (distinct from `device-attest/v1` + `genesis-attest/v1`; a three-way domain-crossing test proves the kinds are non-interchangeable even under the shared attest signing key). A signature proves the head **authentic**, not **current** — two mechanisms turn authenticity into a rollback defence: (a) an **auth-assigned, per-account, strictly-monotone `backup_version`** minted at `POST /auth/backup/head` (bearer-authed + STATEFUL — the `backup_head_versions` counter table, migration `0015`, read-bumped in one transaction via the MariaDB `LAST_INSERT_ID` idiom; never client-supplied, so a regression is structurally impossible) that a **returning client** refuses to go below via a device-key-encrypted `last_known_version` floor (HARD, no window); and (b) a signed **`signed_at`** mint timestamp (Unix millis) a **zero-anchor fresh install** bounds with a client-side staleness window (default 30 days). The head rides as a `0xB1` container-tag prefix of the single storage blob (`crates/lakko-backup/src/head_frame.rs` `frame_backup_blob` / `parse_backup_blob`), so head + envelope swap together in one atomic `PUT` — no torn-state window, no `services/storage` change (invariant #2: the tag + head are more opaque bytes below the storage tier). The three-client restore gate (`verify_backup_head` full / `verify_backup_head_binding`, FFI-exposed with a discriminable `BackupHeadStale` vs `Backup` / `invalid:` error) applies a three-case policy: **absent** (byte 0 ≠ `0xB1` — legacy / stripped) → **fail-open** (rollback-detection availability only — the envelope stays phrase-AEAD sealed regardless, so invariant #4's no-silent-downgrade-to-non-E2EE never depends on the head); **invalid** (bad signature / account / envelope-hash, or a framed-but-truncated blob) → **hard fail-closed**; **stale** (below the floor, or over the window) → **fail-closed with an explicit user-acknowledged override**. Invariants: #1 (the head carries only `account_id`, a `BLAKE3` of ciphertext, a monotone integer, a timestamp; the counter table stores only `(account_id, version)` — no PII), #2 (storage + auth both opaque to key material — auth persists only a counter), #4 (fail-closed, scoped to the rollback-detection layer). ### C-61 — The push-routing-secret rotation is sealed at the post-Remove epoch (ADR-0043)

| ID   | Title |
|---|---|
| C-61 | The [ADR-0043](../adr/0043-push-routing-secret-rotation-on-removal.md) rotation that makes an evicted member's `push_gid` inert (C-60 sub-invariant 6) rests entirely on one **sequencing rule**, pinned separately for the same reason the call-key overlap rules C-8/C-9/C-10 are: **the rotation broadcast MUST be emitted strictly AFTER the Remove commit is published.** The new secret rides an **MLS application message**; emitted at epoch N (pre-removal) the member being evicted is still a member of that epoch and **can open it**, learning the new secret and defeating the whole rotation silently. ### C-62 — Mint-epoch recency ordering for the push routing secret (ADR-0044)

| ID   | Title |
|---|---|
| C-62 | The push-routing secret is **totally ordered** and only a **strictly newer** envelope may displace the stored one ([ADR-0044](../adr/0044-push-routing-secret-recency.md)). C-60 sub-invariant 4 gave the receive path an **authority** gate — *who sent this* — and until this entry there was **no ordering gate at all**, so a **retry** of the current secret and a **replay** of a superseded one were byte-indistinguishable on every client. That omission is what made a **silent, permanent rotation undo** reachable with no malice and no crash (**G-36 residual 9** / `lakko-security` **F-A**, closed by this entry for the single process context). **Five sub-invariants** — four about the order itself, and a fifth about the path that consumes it, added after the arc's own review showed the first four are inert without it. **(1) The order is total, canonical, defined ONCE.** Envelopes are ordered on the pair `(mint_epoch, secret_bytes)` — 8-byte big-endian epoch first, then the 32 secret bytes lexicographically — **strictly greater wins, equal is NOT newer** (what keeps a benign retry from reading as an update and makes the `accept-identical` fast path safe); wrong-length secrets **fail closed to `false`**; never panics. A **live defect in the first implementation**, found by the web verdict tests, fixed on all three with named regression tests. Generalised: **a rule that short-circuits a gate must not write any state that gate protects.** **(5) The gate must run against CURRENT state — its read, decision and persist are serialized per `(account, group)`.** The sub-invariant the arc's own review had to teach it, and the reason the other four are not self-sufficient: the gate is a **read-modify-write** with suspension points between the read and the write, and if two envelopes decide against the **same snapshot** a correct total order changes nothing — the survivor is whichever task wrote last. **Stated generally: an ordering rule is a property of the state the deciding read observed, so a total order is only meaningful if the gate consuming it runs against current state.** Enforcement is **one serializing (never coalescing) lock per `(account, group)`**, held across the whole read-decide-write and **shared** across four entry points — receive, rotate, ensure, **redistribute** (the same read-then-write; unserialized it puts a PRE-rotation secret back on the wire mid-rotation). (b) **Sweeping** — the ADR-0045 committer evaluates it over the authorised pending set and **excludes the role change** rather than publishing a commit every peer would refuse; excluding a role change removes nobody, so one pass suffices with no fixpoint. (c) **On receipt, the boundary** — `process_incoming_verifying_roles` -> `authorise_role_commit` runs it **first**, ahead of the per-proposal loop, against the **pre-merge** roster, and **refuses to merge** (fail-closed, invariant #4) rather than applying and then complaining; a malicious or buggy committer would not run (a) or (b), which is exactly why (c) does not trust it. **What it does NOT do:** it does not recover a **lost** owner (minting a transfer needs the owner's key — it protects a group from being *handed* into an unowned state, and says nothing about an owner who has simply gone; that is still ADR-0022's open admin-quorum question); it is **peer-verified, not cryptographically unforgeable**, so a colluding majority could agree to ignore it, the same leaderless residual ADR-0015 and ADR-0022 both record; and it does not extend to a group with **no role table**, which has no owner to orphan and stays on ADR-0022's open/legacy path (`Group::create` has seeded a table since ADR-0022, so no freshly created group reaches it). **Tests:** `crates/lakko-mls/tests/group_ownership_transfer.rs` (12) — `a_peer_refuses_a_commit_that_hands_the_group_to_a_non_member` and `a_peer_refuses_a_commit_that_erases_the_role_table` for the boundary, `transfer_to_a_non_member_is_refused_locally` for (a), `a_sweep_drops_a_transfer_to_someone_the_same_commit_removes` for (b) and the composed-commit path, `transfer_then_the_former_owner_leaves_and_the_group_works` for the whole intended flow. Invariants **#2** (the role table is an opaque `0xFF02` GroupContext body; the DS relays the commit as ciphertext and parses nothing — unchanged), **#3** (a `crates/lakko-mls` state-machine change under ADR-0045; property-tested, **the `lakko-security` pass ran 2026-08-29 (REQUEST CHANGES, seven findings, all closed); the external crypto review is tracked once in [G-39](known-gaps.md) per [ADR-0046](../adr/0046-external-crypto-review.md) as a release gate**), **#4** (refuse-to-merge, never apply-then-warn), **#5** (roles stay in-group; no server ever learns them). **AMENDED 2026-08-25 by the client sprints (`1de5fe7` / `1f230ab`):** layer (b), the sweep-side exclusion, is **live for the first time** — there was no sweep on any client until then, so it had nothing to run in; layer (c), the receipt boundary, was already live through each client's `processIncomingVerifyingRoles` and is unchanged; layer (a), the authoring pre-check, had **no production caller anywhere**, because no client offered an ownership-transfer affordance — a **UX gap, not a weakening**, since (c) is the boundary precisely because it does not trust (a). **AMENDED AGAIN 2026-09-02:** the transfer flow shipped on all three clients in `0274fa7` (UX §6.1) and each drives `proposeOwnershipTransfer`, which runs `plan_ownership_transfer` before any OpenMLS call — so **all three layers now have production callers**, and "ownership transfer is built" is finally true of the product as well as of `crates/lakko-mls`. | ID   | Title |

| C-64 | **The committer election and the staged sweep decide from authenticated state, and no epoch advances until the journal has ordered it** ([ADR-0045](../adr/0045-remote-commit-epoch-fork.md)). ADR-0022 made a membership change one atomic call — an owner or admin created a commit that **eager-merged before it returned**. ADR-0045 splits it into **propose / sweep / adjudicate**, and every sub-invariant below is something that used to sit *inside* that atomic step and now spans it, which is why they are pinned together rather than one per mechanism. **This entry was deliberately deferred and the deferral is part of its record:** ADR-0045 argued against minting a beacon-shaped invariant while nothing emitted a beacon and nothing drove the fold, because this index describes **live properties** and indexing an inert mechanism would make it aspirational. Both fold inputs are the **observer's own re-derivation**: the sender's rank from the MLS-authenticated sender leaf via `members()` + `Group::committerRank`, and the age from the DS row's **server-assigned** `created_at`, which every member reads identically on the identical row. A self-reported timestamp would let a candidate hold the committer duty by asserting its own freshness — a liveness claim **no peer can check** — so a later hand adding a `sent_at` field "for diagnostics" is a real regression, not a cosmetic one. A beacon whose row timestamp is unparseable is **dropped, not stored as fresh** (stored fresh, it would make the observer defer forever to something that can never age out). **(2) A rank is taken at verdict time, never carried from receipt.** The observation store persists the sender's 32-byte **Ed25519 signature key** — never a leaf index (OpenMLS hands a vacated leaf to the next member added) and never a rank. A rank is a **position** in the role table's canonical order, so promoting, demoting or removing any admin renumbers every candidate sorting after it; a rank captured under one table and compared against one taken under another is not stale, it is a position in a **different ordering**, and nothing in the comparison can notice. `None` and `0` are never interchangeable (`0` is the owner, `None` is not a candidate), and an unreadable rank fails **closed** to defer. **(3) A beacon is emitted only from a client that can actually sweep.** The foreground gate is a **caller obligation the core cannot check** and rests on **C-59**: the ADR-0041 background decrypt is read-only-throwaway, the slim `lakko-ffi-extension` surface does not even export `composeCommitterBeacon`, and a backgrounded process can be frozen at any moment — so a background beacon is a *lie that costs the group a takeover*, since every other candidate defers to a device that is not going to sweep and keeps deferring while the lie continues. Each platform reads "foreground" in its own idiom and none guesses: web treats a missing `document` as **not** foreground; iOS requires **both** screen visibility **and** `applicationState == .active`, because neither implies the other; Android's `repeatOnLifecycle(RESUMED)` scope *is* the gate and still passes the flag through so the rule is written down in one testable place. **(4) The sweep stages; it does not merge until the journal has ordered its commit.** The order is **stand down -> durably record -> publish -> read the verdict -> merge or abandon**. The **stand-down** re-reads the journal head immediately before staging and stands down on **any** unapplied row, not only a commit — deliberately asymmetric, since standing down costs one retry while staging on an unapplied commit costs a commit every peer drops. The **verdict** is read by *applying* the rows below this device's own commit and asking whether the epoch moved; only a commit moves it, so the question needs no content-type discrimination, and guessing permissively would abandon a sweep that **won** and strand the device at N with the group at N+1 holding a commit it can never re-apply (`CannotDecryptOwnMessage`) — the same brick in reverse. An **unreadable verdict leaves the sweep staged**: merging on an unread verdict is the eager shape this ADR removes, and abandoning would discard a commit already on the wire. Rollback is **per-group** (`clear_pending_commit`), never a whole-provider `restore_storage` that would roll sibling groups back past commits they have published. **(5) The Welcome is published only after the verdict, and a staged sweep is owed one.** A Welcome released for a commit that then loses lets a joiner open into a state **no member holds** — a three-party fork, strictly worse than the two-party one this ADR closes — so its bytes and mailbox pseudonyms are computed at record time and sent only on the **merge** branch. And because a staged commit is **durable** (`MlsGroupState::PendingCommit` via `write_group_state`) and freezes that group's `propose_*` / add / remove / `self_update` through `is_operational()`, a sweep that never reaches a verdict wedges membership **across restarts** — so every sweep adjudicates what it staged, an owed verdict is resolved at restart through ADR-0040's existing `sweepPendingCommits` seam rather than a second restart path, and the owed-verdict check runs **ahead of** the acting-committer rank check (an admin can be demoted while holding a staged sweep, and gating the resolution behind the rank check would freeze that device permanently; re-publishing is safe because peers refuse a demoted author's commit, so it loses and is abandoned, which is the unwedge). **What this does NOT claim.** It is **not a leader election and does not make one** — each candidate folds over its own poll-timed view and a beacon is stale by up to one interval even when its sender is healthy, so two candidates can both reach `Act`; the heartbeat removes the *wait*, not the *race*, and sub-invariants 4 and 5 are what make a collision survivable. A **forged or replayed beacon buys nothing but a deferral** (no key material, authorises nothing), which is a liveness effect of the class this pack tracks as a gap; the confidentiality-shaped half of this entry is sub-invariant 5's Welcome rule. The **freshness window is met on all three platforms** — it is `2 x interval + worst-case poll`. This used to read "two platforms of three": the web client had **no periodic poll** (mount, a user action, the Refresh button), so a web observer could see a beacon well after the window it was sized for. The web chat route now runs an automatic receive loop — a DS long poll with a 25 s `wait` (`apps/web/src/ds/long-poll-loop.ts`), below the 30 s worst-case poll the window is sized against — while the chat is open and the tab is visible, or during a call; that is the same foreground condition the web beacon emitter already required, so a web candidate that is beaconing is also observing. The **constants are chosen, not measured** (60 s interval, 150 s window), resting on a stated budget argument about journal litter and activity-schedule exposure. **Where it lives:** `crates/lakko-contacts/src/committer_beacon.rs` (33 in-module tests plus the `committer_beacon_decode` fuzz target, which drives the **fold** from the same attacker-controlled bytes and asserts a `None` own-rank is always `NotACandidate` and a `Defer` never names a rank at or above the observer's own), `crates/lakko-mls/src/group.rs` (the staged pair) and `group_roles::committer_rank`; clients in `apps/web/src/chat/{sweep,committer-beacon}.ts`, `apps/ios/Lakko/Chat/{CommitterSweep,CommitterBeacon}.swift` and `apps/android/.../chat/{CommitterSweep,CommitterBeacon}.kt`, each over injected ports so the orchestration runs in a plain host test environment, and each carrying probes whose **discrimination was measured by running them and recording the failure** (hoisting the Welcome above the verdict, merging instead of abandoning on a loss, putting the owed-verdict check back behind the rank check, deleting the foreground gate, carrying a rank over from receipt). The predicate is **stateful**, so each pass over the pending set needs its own flag — the emptiness prediction and the real filter must not share one, or the prediction would spend the budget the filter needs. **The second half is NOT made redundant by the first, and this is the part a later hand will get wrong:** the propose-time guard cannot see a state that arises **legitimately** — a device that publishes a role-change proposal and then loses its own record of it before persisting (the ADR-0040 crash window) proposes a second one in good faith, and every *peer* then holds two; without the sweep-side bound those peers can never sweep again. ## How to add a new invariant

Adding a new invariant means **all five** of the steps
below — drift between this index and the source files is
the audit-grep failure mode this page exists to prevent.

1. Decide which class — `I-` (MLS), `C-` (calls /
   channels — everything the SFU/channels server might
   see), `T-` (transport), `G-` (gap, not yet a real
   invariant).
2. Pick the next free integer. The class is namespaced —
   `C-45` and `T-12` are both legal next IDs at any time.
3. Add the invariant to its source file in this audit
   pack. Convention: `### {ID}: {Title}` followed by a
   short rationale + pinned tests / code references.
4. Add a row in **this** index — same ID, same title.
5. If the new invariant supersedes an old one, edit the
   old row to mention the supersession (don't delete —
   the row's removal would break grep + historical
   commit-message links).

**Adding or renumbering a `G-` gap takes two extra edits**,
both on this page, because the `G-` class alone is gated on
its totals: update the **count and range** in the `G-` row
of the Quick stats table — `just audit-index-check` derives
both from `known-gaps.md` and **fails** on a mismatch — and
adjudicate the **`Total open gaps`** row by hand, which the
gate deliberately does not check (see the note under Quick
stats for why).

## Counter sanity checks

If `wc -l docs/security/{calls,transport,mls-state-machine,known-gaps}.md`
goes up significantly without this index changing, an
invariant landed without being indexed. **CI gates on
this** via [`tools/audit-index-check`](../../tools/audit-index-check)
— a bash script that diffs the `### {class}-{n}:` headers
in the four source files against the per-class tables on
this page. Both directions are checked: a new invariant
in the source must have a matching index row, and a stale
index row whose source-file header is gone is also a fail.
The `G-` class additionally has its **total and range in
the "Quick stats" table checked against the source**, so a
hand-written count cannot drift; the `Total open gaps` row
is deliberately excluded, because a gap's status is an
adjudication rather than a mechanical fact (see the note
under Quick stats). Wired into `just ci` as the final docs
gate. Run locally via `just audit-index-check`.
