# Lakko — AI-agent navigation

This file is loaded into the context of every session automatically. Keep it short and precise; details live in `docs/adr/` and in the plan at `~/.claude/plans/1-nested-wreath.md`.

## What Lakko is

A Telegram-class secure messenger with **E2EE by default for everything** (1×1, groups, channels, audio / video calls, broadcasts, audio rooms). Zero-trust server. All clients share a single Rust core + native UI.

| [0015](docs/adr/0015-device-removal-authorization.md) | Device-removal authorization (G-13). Threat analysis: a DeviceGroup `Remove` commit is signed by the per-device MLS key (seed encrypted under a non-extractable device key, invariant #7), so a remote token-only attacker **cannot** forge a removal — peers reject an invalid signature — which already closes the token-replay threat. The DS is opaque + the auth service is never in the removal path, so there is no server request to gate; the residual is on-device malware that bypasses the UI. **Decision: implement** peer-verified attestation — `services/auth` signs a compact Ed25519 attestation over `(account_id, action_hash, expiry)` on `/auth/action/finish`, carried alongside the `Remove` commit + verified in the `lakko-mls` apply path. Sprints 1–2 landed: the `lakko-attest` crate (format + sign + `verify_bound`); a dedicated attestation Ed25519 key in `services/auth` (migration 0010, generated on first boot, separate from the call-JWT key), `/auth/action/finish` signs + returns `attestation_b64` (1 h TTL), verifying key published at `GET /.well-known/device-attest-jwks.json`. Sprint 4 landed: the OPAQUE-only policy flag is wired into `lakko-mls` — device KeyPackages + DeviceGroup founders advertise the removal-policy `Extension::Unknown` capability, DeviceGroups carry `required_capabilities` for it from creation, `DeviceGroup::set_require_attested_removals` flips it on via a GroupContextExtensions commit + `require_attested_removals` reads it (property test proves propagation to a joined device). Sprint 3 landed: the apply-path verification — `Group::process_incoming_gated` surfaces a Remove commit's removed `(leaf, signature pubkey)` pairs before merge, and `DeviceGroup::process_incoming_verifying_removals` **refuses** (won't merge) a removal under the policy unless a removed leaf is covered by a valid `lakko-attest` attestation bound to the account + `SHA-256("lakko/action/remove-device/v1" ‖ pubkey)` + freshness (6 property tests: valid/missing/wrong-leaf/wrong-key/policy-off/non-remove). Sprint 5 FFI surface + web wiring landed: `setRequireAttestedRemovals` / `requireAttestedRemovals` / `processIncomingVerifyingRemovals` / `removeDeviceActionHash` exposed on UniFFI (Swift/Kotlin) + wasm (web); web threads a DeviceGroup journal envelope (`version‖attestation_len‖attestation‖mls_message`) — `Devices.tsx` captures the attestation, every `publishGroup` site wraps, the `DeviceGroupSyncContext` receive loop unwraps + applies via `processIncomingVerifyingRemovals` against the fetched device-attest JWKS key (zero-key fail-closed fallback). iOS + Android wiring landed too — Swift/Kotlin `DeviceGroupJournalEnvelope` + `DeviceAttestKey` + the same capture/wrap/receive-loop shape (`xcodebuild` green after an `xcframework` rebuild; `:app:compileDebugKotlin` green). the policy is now auto-enabled — all three clients call `setRequireAttestedRemovals` (idempotent GroupContextExtensions commit) right after a passkey is first registered (`enableAttestedRemovalsIfNeeded`), so G-13 is implemented end-to-end (server attestation + peer-verified apply path + 3-platform transport + auto-enable). key pinning landed too — each `DeviceAttestKey` client accepts a build-time pinned verifying key (`VITE_LAKKO_DEVICE_ATTEST_KEY` / Info.plist `LakkoDeviceAttestKey` / `BuildConfig.LAKKO_DEVICE_ATTEST_KEY`); when set it never consults the JWKS endpoint (defends a compromised serving tier, not a compromised signing key). G-13 fully implemented; the only optional residual is distributing the pinned key via the signed bootstrap config (needs Phase-5 client bootstrap consumption, out of scope) |
| [0016](docs/adr/0016-identity-supersession-transport.md) | Identity-supersession proof transport (G-4, invariant #6). The proof primitive + verifier + FFI already landed (sprints 1–3); this ADR picks the **carrier**. **Decision: Carrier B — the discovery identity bundle (pull).** The proof rides in the user's `identity_bundles` row (already re-published on recover), and a peer re-observes the account key only when it **fetches** the bundle, so verify-and-re-pin happens in the same response — no new transport, routing, or persistent secrets. Carrier A (new DS-mailbox envelope, push) rejected: the mailbox `IdentityPseudonym` is account-key-derived so the old inbox dies on rotation, and the rotation-surviving per-relationship pseudonym is unpersisted (push deferred as future work behind the KT-log chain verifier). Sprint 4 audit: recover-from-words is the only AccountIdentity rotation path (no change-password flow exists), so the emit is correctly placed. Remaining: a `lakko-security` pass on the verify path (explicit-request gate) + a live cross-platform 2-device e2e (no deployed environment) |

## Security invariants — must not be violated

1. **No plaintext PII on the server.** Phone / email are **never** stored — not even encrypted. Only OPAQUE-blinded records and a hash for recovery.
2. **The server only sees ciphertext + public artefacts** (KeyPackages, transparency-log entries). No message keys, chain keys, root keys, media keys.
3. **The MLS state machine is sacrosanct.** Any change to `lakko-mls` requires an ADR + property tests + (after Phase 2) an external crypto audit.
4. **No fallback to non-E2EE.** Strict E2EE only — if the handshake does not complete, the connection does not open. No silent downgrade.
5. **The social graph is not materialised on the server.** Add-contact = encrypted envelope to a pseudonym; presence — blinded per-conversation tokens; discovery — OPRF blinded lookup.
6. **Identity rotation** — only via a KT log supersession proof. Old keys do not come back.
7. **Hardware-backed device keys** are mandatory on every platform (Secure Enclave / StrongBox / TPM 2.0 / non-extractable WebCrypto).

- **`lakko-attest/attestation_open`** — `ActionAttestation::open(bytes, verifying_key)` (G-13, [ADR-0015](docs/adr/0015-device-removal-authorization.md)): the device-removal attestation parser — a fixed-layout 121-byte blob (`version‖account_id(16)‖action_hash(32)‖expires_at(8 BE)‖sig(64)`) that arrives ALONGSIDE a peer's DeviceGroup `Remove` commit, so a malformed envelope is fully attacker-controlled and reaches this bounded parser before any state is consulted. Opened against a FIXED verifying key (the fuzzer cannot forge a valid Ed25519 sig, so it exercises the length / version / field-slicing / signature-parse / verify-fail path)
- **`lakko-sync/sync_replay`** — the multi-device sync receive path (`fuzz_api::replay_and_check`). `lakko-sync` carries no on-the-wire byte parser of its own (the DeviceGroup substrate owns deserialization, Phase 2); the attacker-relevant surface is the LWW / HLC **logic** fed by a peer device's ops after AEAD-open. The harness decodes the fuzz bytes into a receive sequence of adversarial `Hlc` stamps + ops and asserts the ordering-integrity invariants a malicious/compromised peer must not break: HLC monotonicity (`tick` / `merge_remote` never wind the local clock backwards), `EditChain::merge` == append (documented commutativity), and resolve idempotence — a property oracle, not a parse-crash target (the arithmetic is already saturating). Order-independence under HLC ties is deliberately NOT asserted (`current` tie-breaks by vector position by design)
- **`lakko-push/push_decode_json`** — `PushPayload::decode_json(bytes)` (`fuzz_api::decode_push_payload`): the on-device push-payload parser. A push notification's `data` payload is relayed verbatim by the OS push pipeline (APNs / FCM / UnifiedPush) and decoded on wake-up before any further processing, so the input is fully attacker-controlled. Drives the full pipeline — `serde_json::from_slice` → the schema-version gate → the kind dispatch (`g` / `m` / `w` + field-presence rules) → the base64 pseudonym decode + 32-byte length check
- **`lakko-attachments/message_body_parse`** — `parse(bytes)` + `parse_body(bytes)` (`fuzz_api::parse_message_body`): the receiver-side MLS Application message-body decoder. A malicious or compromised group member can craft arbitrary envelope bytes, which reach this decode path on receipt before any rendering. Drives the full receive chain — `serde_json::from_slice::<Envelope>` → the schema-version gate → the bare-UTF-8 `from_utf8_lossy` fallback → the per-ref base64 decoders (`decode_blob_id` / `decode_key` / `decode_nonce`, each a base64 decode + fixed length check) on every decoded reference — AND (ADR-0023/0024) the `parse_body` classifier: the `edit_of` / `delete_of` / `react_to` / `typing` / `read_up_to` op fields, the `MAX_EMOJI_BYTES` cap, and the >1-op-field / reaction-without-emoji fail-closed degrade-to-`Chat` paths
- **`lakko-auth-token/token_verify`** — `TokenSecret::verify(token, now_ms)` (`fuzz_api::verify_token`): the HMAC-SHA256 session-token parser + verifier. A client or peer presents this token to the server on every protected discovery request, so the token string is fully attacker-controlled and reaches the parser before admission. Verified against a FIXED 32-byte secret (the fuzzer cannot forge a valid HMAC, so it exercises the dot-split → version gate → base64url account_id decode + 16-byte length check → `i64` expiry parse → base64url tag decode + 32-byte length check → HMAC compute + constant-time compare → expiry check). UTF-8 gate at the harness edge keeps coverage on the token parser
- **`lakko-shamir/share_decode_combine`** — the social-recovery share parse + reconstruct path (`Share::decode` + `combine`, via `fuzz_api::decode_and_combine`). Shares are distributed to and later collected from peers / guardians, so a malicious holder can submit crafted share strings. The harness treats the input as newline-separated candidate shares, decodes each via the `<index>:<base64>` parser, and `combine`s the decoded set — exercising the share-count / length / duplicate-index guards and the GF(256) Lagrange interpolation (the duplicate-index check is what keeps the field division from dividing by zero; the unique-index space is `u8`, so the quadratic `combine` work is naturally bounded)
- **`lakko-mnemonic/mnemonic_parse`** — the BIP39 recovery parsers (`Mnemonic::from_phrase` + `from_entropy`, via `fuzz_api::parse_mnemonic`). `from_phrase` parses a user-typed / device-relayed recovery phrase; `from_entropy` reconstructs from `lakko_shamir::combine` output, which a malicious guardian's shares can influence. The harness runs both on the same input — the raw bytes through `from_entropy` (32-byte length gate → BIP39 checksum reconstruction) and, when valid UTF-8, the string through `from_phrase` (24-word count gate → wordlist lookup → checksum)

The `fuzz_api` module in `lakko-mls` (marked `#[doc(hidden)]`) is the only public entry point for harnesses; it is not part of the supported public API.

Fuzzing corpora are not committed (`fuzz/corpus/`, `fuzz/artifacts/` are gitignored); they are spun up locally.

The `.github/workflows/fuzz-quick.yml` workflow actually RUNS every fuzz target for a bounded budget (60s default, configurable via `workflow_dispatch`) on nightly cron (03:00 UTC) — `just fuzz-check` only smoke-builds. Matrix runs one job per fuzz crate (10 jobs, ~32 targets total); crashes upload to the workflow run page as 14-day-retention artifacts. Concurrency limited to 1 so overlapping nightly runs don't pile up.

## Specialized skills — routing (read BEFORE writing code)

This repo ships domain-specialist skills under `.claude/skills/`. They carry the per-area invariants, build commands, and review checklists so you do not rediscover them each turn. **Routing is mandatory, not optional** — before editing files in an area, invoke the owning skill via the `Skill` tool so its SKILL.md loads into context. This OVERRIDES the default "just start editing" behavior.

| When the task touches… | Invoke this skill FIRST |
|---|---|
| `crates/` or `services/` (general Rust) | `rust-core` |
| `services/sfu/` or `crates/lakko-calls/` (SFU / media / SFrame) | `sfu-media` |
| `apps/ios/` | `ios-client` |
| `apps/android/` | `android-client` |
| `apps/web/` | `web-client` |
| `infra/` or deploy / ops | `infra-deploy` |
| Writing tests, running a verification pass, triaging a failure | `qa` |
| Designing / reviewing a user-facing screen or flow, cross-platform UI consistency | `ux-ui` |
| An architectural decision (new crate / protocol / schema migration / security-model change), writing an ADR, or keeping docs (ADRs / module map / ROADMAP / invariant index) in sync | `architecture` |
| A task spanning >1 area, or unsure which area owns it | `lakko-dev` (coordinator — it classifies, routes, and sequences cross-cutting work) |
| Reviewing security-sensitive changes (crypto / MLS / transport / auth) | `lakko-security` (run ONLY on explicit maintainer request — never auto-gate) |

Rules:
- **Single-domain task** → invoke the one owning skill, then do the work.
- **Cross-cutting task** (e.g. a Rust change wired through FFI to all 3 clients) → invoke `lakko-dev` and let it sequence the work (schema → Rust core → FFI → parallel client fan-out → verify) via sub-agents.
- The background skills (`rust-core`, `ios-client`, `android-client`, `web-client`, `sfu-media`, `infra-deploy`) are model-invocation only — YOU must call them; they do not self-trigger by path. Skipping the routing step is a process violation.
- `lakko-security` is an explicit-request gate. You MAY remind the maintainer it is available when crypto/MLS/transport/auth is touched, but do NOT run it unprompted.

## Workflow for the AI agent

- **Skill routing first** — before editing code, invoke the owning specialist skill per the routing table above (or `lakko-dev` for cross-cutting work). This is a hard step, not a suggestion.
- **Plan mode** for architectural tasks (a new crate, a protocol change, a schema migration)
- **TodoWrite** for multi-step tasks (>3 steps)
- **Do not bake in future features** — write for the concrete task at hand. The spec roadmap lives in the plan; we implement phase by phase
- **When in doubt about security-critical code** — stop, ask, do not guess
- **Subagents** (Explore, Plan) — for broad research, not for trivial edits
- **Do not commit without a signature** — `commit.gpgsign = true` is required on this repo
- **Russian-chat commit-message rule** — when the interactive chat is in Russian and the turn produced changes in code or documentation (anything `git status` would show as modified / added / deleted), the assistant MUST end its reply with a ready-to-paste English commit message in a fenced block. Skip the block only when there are no file changes.
- **No AI signature lines in commit messages.** Never append `Co-Authored-By: Claude …`, `Generated with Claude …`, or any similar attribution footer to commit messages or PR descriptions. The maintainer authors the commit.
- **No emoji / icons in commit messages or logs.** Commit messages, PR descriptions, and every log line emitted via the `tracing` crate from **any** client app (web / iOS / iPadOS / macOS / watchOS / Android / desktop) **and** every backend service (`services/*`) MUST be plain text — no emoji, no Unicode pictographs, no decorative icons. ASCII-only structured prefixes (`[auth]`, `OK`, `WARN`, `ERR`) are fine; emoji like `✅` / `❌` / `🔒` / `🚀` are not. Applies to user-visible release notes the maintainer drafts from these as well.
- **NEVER fabricate numbers, metrics, estimates, or facts.** Hard rule. Forbidden examples that the assistant has previously violated and MUST NOT repeat:
  - Cost / value / ROI dollar figures invented for rhetorical effect (`"$1500 of value for $400 of work"` with no underlying model).
  - Performance numbers, latency / throughput / memory budgets pulled out of thin air to back a recommendation.
  - Bug counts, defect rates, percentage-of-users-affected, MTTR estimates without a data source.
  - LOC counts, time-to-ship estimates, sprint sizing presented as confident when they are guesses.
  - Citation-shaped references (`per RFC 1234 §5`, `per ADR-0099`) that are not actually verified by reading the source.
  - Commit-message claims about what the commit does — every line must match what `git diff` actually shows.
  - Test-result summaries when tests were not actually run (`"all green"` when nothing was executed).
  - Claims that something is `done` / `green` / `passes` when it has not been observed firsthand in this session.

  When the assistant does not have a real basis for a number or fact, the correct shapes are: `"I do not know"`, `"my rough guess is N — not verified"`, `"the order of magnitude is X based on Y, the precise value would need a measurement"`, or simply omitting the unsupported claim and proceeding without it.

  When a fact CAN be verified cheaply (read a file, run a command, look at git history), the assistant MUST verify before stating it. Fabricating facts that could have been checked is the same violation as making them up out of nowhere.

  Recommendations and prioritisation calls are allowed without quantification — `"my hunch is iter2a first because it does not touch ICE/DTLS"` is honest. `"iter2a delivers $1500 of value"` is not.
- **No LOC counts in chat.** The maintainer does not care how many lines of code the AI generates. Do NOT report "~600-800 LOC" / "~200 LOC per platform" / "small sprint ~50 LOC" as a way to signal sprint size or complexity. This was a habit the assistant used to project rigour; it just clutters the chat with a metric that does not measure anything the maintainer is evaluating. If sprint sizing must be discussed, talk about it in terms of risk surface, number of integration points, blast radius of a regression, debug cost of flaky failures — anything but a line count. Counting actual diff lines AFTER a commit is fine when the maintainer explicitly asks ("how big was that?"); volunteering it as a size proxy in a recommendation is not.
- **The maintainer decides what to work on next; the assistant proactively proposes the options.** The maintainer should NEVER have to ask "что дальше / what's next" — at the end of every completed unit of work (a sprint, a fix, a closed task), the assistant ends its turn by presenting the next candidate steps so the maintainer can just pick. Use `AskUserQuestion` (the clickable menu) for this by default — it is exactly a "choose the next step" decision and is the path of least friction. List the highest-value option first with an honest one-line trade-off (no fabricated value/impact), cover the genuinely distinct directions (e.g. finish the current arc vs. switch areas), and keep "Other" implicit. Do NOT silently pick the next sprint and execute it without offering the menu — choosing the direction is the maintainer's call, not the assistant's. The assistant's job is to make that choice cheap: surface the options unprompted, recommend, and wait for the pick. (Within a step the maintainer has chosen, the assistant still drives all the sub-work autonomously and only stops to ask on a genuinely security-critical/irreversible decision per the "stop, ask, do not guess" rule.)

## Technical invariants

- **Rust edition 2021**, toolchain pinned to an exact stable release in `rust-toolchain.toml` (currently `1.95.0` — NOT the floating `stable` channel, so a rustfmt/clippy bump cannot silently drift; the CI workflows pin `dtolnay/rust-toolchain@1.95.0` and the `build-ios` / `build-android` recipes self-heal the cross-targets, all in lock-step). Bump deliberately + re-run `just fmt` + `just lint`
- **Cargo workspace** — a single `Cargo.toml` at the root, all crates and services live inside it
- **Workspace dependencies** — versions of shared deps pinned in `[workspace.dependencies]`, crates inherit via `dep.workspace = true`
- **Reproducible builds** — the Nix flake pins the entire toolchain; CI checks byte-identicality between runners
